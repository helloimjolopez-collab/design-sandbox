Horizon — Case Status Architecture

Production current state · V1 replatforming target

Mental model: transactions, not cases or people One row per order. No persistent person record. No concept of a "case." The Status field conflates invite link state, consent state, order processing state, and report state into a single field. Assessment (the admin's judgment on the report) is tracked in a separate column. Rescreening health is tracked in yet another column. These are not connected into a coherent lifecycle — they are fragmented signals displayed side by side.

No approval gate in production today Manual orders exist (admin fills in applicant data directly, pulling from previous check data or entering manually), but there is no flow where an applicant fills in their own consent form and that form is then held for admin approval before ordering. The approval gate concept is future state only.
Mental model: Cases Every screening engagement and every training engagement is a Case. There are two types: Screening Cases and Safety Training Cases. A person can have many cases over time. Each case has exactly one lifecycle status that tracks the full arc from first action to final outcome — including the admin's assessment and long-term rescreening or retraining health. There is no separate Assessment column. There is no separate rescreening indicator. The case status says everything about where that case stands right now.

Current — fragmented

  • ✕Status field: invite + consent + order + report — all one field
  • ✕Assessment in a separate column, disconnected from lifecycle
  • ✕Rescreening health in yet another indicator
  • ✕No approval gate phase — consent received has no distinct status
  • ✕Report returned looks the same as report assessed
  • ✕No concept of case or person — one row per order

V1 — unified case lifecycle

  • ✓One status tracks the entire case from link to final outcome
  • ✓Assessment outcomes (Complete: Cleared, Complete: Escalated) are lifecycle statuses
  • ✓Rescreen/retraining health is part of the case lifecycle
  • ✓Approval gate is an explicit lifecycle phase with its own status
  • ✓Report complete and awaiting review is a distinct, actionable status
  • ✓Every case is anchored to a persistent person record

Screening Cases — V1 lifecycle

One case per screening context. Each case is linked to one person, one department, one check type. The status below tracks that case from the moment it is created to its final resting state. Assessment outcomes fold into the lifecycle — no separate column.

Invite / consent collection
Invite Link Created Consent No A person-bound invite link has been generated. No email has been sent yet. Admin holds the link and will send it through their own channel. Admin sends link → Invite Link Sent. Admin cancels link → Invite Link Cancelled. Admin cancels case → Case Cancelled.
Invite Link Sent Consent No PMM sent an invite email to the applicant. Waiting for the applicant to submit their consent form. Applicant submits consent → Consent Received (or Consent Received — Awaiting Approval if gate on). Expiry approaches → Invite Link Expiring. Expiry passes → Invite Link Expired. Email bounces → Invite Email Bounced. Admin cancels link → Invite Link Cancelled. Admin cancels case → Case Cancelled.
Invite Link Expiring Consent Prompt The invite link is approaching its expiry date. Applicant has not yet submitted consent. Admin should resend or extend before the link dies. Applicant submits before expiry → advances normally. Expiry passes → Invite Link Expired. Admin extends → back to Invite Link Sent. Admin cancels link → Invite Link Cancelled. Admin cancels case → Case Cancelled.
Invite Link Expired Consent Yes — re-invite The invite link reached its expiry date with no consent submitted. The case is stalled. Admin must re-invite to restart or cancel the case. Admin re-invites → new link generated, status resets to Invite Link Sent. Admin cancels case → Case Cancelled.
Invite Email Bounced Consent Yes — fix address The invite email could not be delivered to the applicant's address. Admin must correct the email and resend, or switch to a generated link. Admin corrects email and resends → Invite Link Sent. Admin switches to link → Invite Link Created.
Invite Link Cancelled Consent No Admin cancelled this specific invite link. The case itself is not necessarily closed — admin may issue a new link. No consent was submitted on this link. Admin issues new link → Invite Link Created or Invite Link Sent. Admin closes case → Case Cancelled.
Case Cancelled Consent No — terminal Admin cancelled the entire case. No check will be ordered. Case record is retained for audit history. Terminal.
Consent received
Consent Received Consent No Applicant submitted their consent form. No approval gate is active for this department. Order will be placed automatically. System auto-places order → Order Processing.
Consent Received — Awaiting Approval Consent Yes — approve or hold Applicant submitted their consent form. The approval gate is active for this department — an admin must explicitly approve before the order is placed. If a name mismatch is present on the consent form it is surfaced prominently here before the approval buttons appear. Admin approves → Order Processing. Admin holds → stays here. Admin requests correction → invite re-issued to applicant.
Order and processing
Order Processing Processing No Background check order has been submitted to Digital Delve and is actively being processed. No admin action required. DD returns report → Report Complete — Awaiting Review. DD returns an error → Order Failed.
Order Failed Processing Yes — retry or support The order could not be submitted to or processed by Digital Delve. A technical error occurred. Admin must retry or contact support. The case is not stuck permanently — admin has an explicit action available. Admin retries → Order Processing. Admin cancels case → Case Cancelled.
Report complete — admin review required
Report Complete — Awaiting Review Review Yes — review report Digital Delve returned the completed report. Admin has not yet reviewed it and recorded an outcome. This is an action-required case. The report is accessible from this status. Admin records outcome → Complete: Cleared or Complete: Escalated.
Terminal outcomes — assessment folded in
Complete: Cleared Outcome No — terminal Admin reviewed the report and cleared this person for the role. No disqualifying findings. Case is resolved. Rescreening clock starts from this point if a rescreen interval is configured for this person's role or department. If rescreen interval is set: advances to Rescreen Due when date approaches, then Screening Expired when date passes.
Complete: Escalated Outcome Yes — do not activate Admin reviewed the report and escalated. This person must not be placed in the role. The most serious terminal outcome. FCRA adverse action process may apply. Terminal. Record retained. Adverse action flow triggered if applicable.
Rescreening health — part of the case lifecycle
Rescreen Due Health Prompt The rescreening date is approaching based on the configured rescreen interval. The current check is still valid. Admin should initiate a new screening case soon. Admin initiates new screening case → new case created. This case remains Rescreen Due until the new case is active or the date passes.
Screening Expired Health Yes — rescreen now The rescreen due date has passed with no active new screening case. This person's screening is no longer current. A new background check is required before they continue serving. Admin initiates new screening case → new case created. This case status remains until the new case completes.
Manual orders in V1 When an admin places a manual order (no invite flow), the case skips the Consent phase entirely. The case opens directly at Order Processing. Authorization is recorded separately by the admin as a required step before the order is placed. The case lifecycle from Order Processing onward is identical to an invite-based case.

Safety Training Cases — V1 lifecycle

One case per training engagement. Same case-based mental model as Screening Cases. Status tracks the full arc from invite to certification and beyond.

No "In Progress" case status When an applicant opens the training link or begins working through the module, that event is recorded as a timestamped entry in the case timeline (visible in the applicant's detail view). It does not change the case status. The case continues to show its current invite link status — Invite Link Sent, Invite Link Expiring, etc. This means an abandoned training is not invisible: the invite link will eventually expire and the status will advance to Invite Link Expiring then Invite Link Expired, which prompts the admin to take action. If "In Progress" were its own status, abandoned trainings would silently pile up with no indication that action is needed.

What V1 resolves that current state cannot Every status describes exactly one condition. Admin knows precisely what is happening and what action (if any) is required without opening the record. Assessment outcomes are final lifecycle statuses — not a second column to cross-reference. Report complete and awaiting review is explicitly visible in the table. Approval gate consent is an explicit phase. Invite link expired vs screening expired are clearly different statuses with different names. Rescreen and retraining health are part of the case, not orphaned dashboard indicators. Invite Link Cancelled and Case Cancelled are distinct — cancelling a link does not automatically close a case. Abandoned trainings surface through link expiry, not through a silent "In Progress" pile. Every case flows from a person record, so the history of all cases is aggregated per person.
