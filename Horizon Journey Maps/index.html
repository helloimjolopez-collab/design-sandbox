😤Pain Points
 No way to filter the main table by tag or role, select a cohort, and initiate checks in bulk — each order must be started fresh from the invite wizard. Nothing in-product helps distinguish who needs screening, who is already covered, or who is a duplicate. The person search-and-select behaves neither like a standard combobox nor a person-picker. No serving context (role, department, tags) visible. No screening status at point of adding — no indication of a check in progress, a cleared check on file, or a case awaiting review. Abandoning mid-flow loses all progress with no save or resume. Package dropdown has no descriptions and no role guidance. Coordinators cannot tell at a glance what level suits a given role. No explicitly labeled 'Don't include CST' option. State dropdown: purpose at this step is not explained. Billing Reference is a dropdown, not free text — if the expected code is not listed, nothing on this screen adds one. CST Email Template column renders a required asterisk even when CST was not ordered. Preview shows wrong sender address. No edit shortcut — correcting a value means walking the whole stepper back. 'Send Invites' labels this as email delivery but it is actually record creation, a billing event, and email dispatch simultaneously. FCRA text looks like legal boilerplate, not a commit gate. Success screen has one CTA: 'Done.' Returns to an empty dashboard. No in-product receipt. Admin confirmation email arrives ~1 minute later with only the applicant's name — no package, state, total, or billing ref. Logo broken in both emails.
💡Opportunities
 Visibility of who is already covered, who is new, who might be a duplicate. A recognisable starting line for a process that usually begins outside the product. A standard person-picker with an explicit 'add new person' pattern. Serving context (role, department) visible at point of selection. Screening status chip: In progress / Cleared / Expired / None. Duplicate detection before commit. Three platform screening levels each showing a risk label, the type of roles it suits, and role examples. CST as an explicit on/off toggle. State field purpose clarified or removed if not needed at this step. Preview that matches what applicants actually receive. CST email template hidden when no CST was ordered. Billing Reference that connects to what finance actually expects. Commit point legibility: label Send clearly as the action that creates records, fires emails, and opens a billable order. Ability to correct a single value without rewinding the stepper. A lasting in-product receipt: who was ordered, which level, which state, which billing code, when invites expire. Cases visible in table immediately after commit.
💭How Might We
 How might we help staff arrive knowing which cohort needs screening, who is already covered, and whether any are duplicates? How might we make it visible, before commit, whether each row will merge with an existing person or create a new one — and catch typos while the user is still on this step? How might we give coordinators enough in-context information to pick a level that clearly matches the role's risk profile, without calling support or consulting an external cheat-sheet? How might we show a preview that matches what applicants will actually receive, and hide the CST template when no CST was ordered? How might we make 'Send Invites' unambiguously the commit point, and let staff correct a single value without re-walking the stepper? How might we give staff an in-product record that answers 'what did I just send, for whom, under what level, at what cost code' without a login-gated click-through?

What changes

4 steps instead of 6. Flow starts with who, not which method. Person picker shows serving context and screening status before any order is placed. Commit point is clearly labeled.

Screening levels

Platform levels (Basic, Enhanced, Comprehensive) plus account-configured custom levels and add-ons. Each shows a risk label, the type of roles it suits, and role examples. Information, not recommendations. Enough context to choose without calling support.

Commit point

"Confirming creates a background check case for each person listed." Labeled explicitly above the confirm button. Person records and cases created on confirm, not before.

Rescreening adoption gap
Current: less than 10% of PMM customers actively rescreen. Reactive discovery, one-at-a-time wizard, level re-selected from memory.
Why highest impact: the product architecture is the primary barrier to a safety-critical practice the product is supposed to enable.
Bulk ordering
Current: 107 applicants due for rescreen requires 107 separate wizard runs. No bulk path exists.
Why highest impact: removes the single biggest friction point in the rescreen workflow. Pre-filled levels remove the second biggest.
Proactive notification
Current: Sarah discovers the queue by checking proactively. No system-generated alert before checks expire.
Why highest impact: reactive discovery means rescreens are initiated late or not at all. Proactive notification shifts the default from reactive to systematic.

What changes

Proactive notification before checks expire. Named queue sorted by urgency, filterable by department. Bulk selection and batch reorder in one session. Package pre-filled from last cleared check.

Adoption gap addressed

Less than 10% of churches actively rescreen today. The main barrier is effort: discovering who is due, ordering one by one, re-selecting the same level from memory. Bulk ordering with pre-filled levels removes most of that friction.

Interval configuration

Rescreen interval configurable per role or department (1yr / 2yr / 3yr), not just a single global account setting. Due dates recalculate automatically when a new check clears.
