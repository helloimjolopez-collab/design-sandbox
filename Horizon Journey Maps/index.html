Execution Plan

Project Horizon 2.0 · Two parallel tracks converging at the Horizon rebuild · Updated June 2026

How the two tracks work

Track 1 and Track 2 run in parallel — neither waits for the other to complete. Track 1 produces the Pathway component library (ValueLabs builds to MB spec). Track 2 produces the service blueprints, domain model, API architecture, and finalised product design decisions (MB engineering). The Horizon rebuild is the convergence point where both tracks' outputs are consumed. It does not begin until both tracks have cleared their gate conditions.

Track 1 Underway

Component Build Acceleration

ValueLabs builds Pathway components to MB spec in Figma. Ministry Brands owns, reviews, approves, and deploys everything. VL has no repo access.

1a
Standards delivery + Table pilot

MB delivers the component list, build standards package, and handoff process documentation. VL audits the live application to confirm full coverage. VL then builds the Data Table as the pilot component — fully to MB standard before any other component begins.

⚑ Pilot gate: MB design lead reviews the Table against all criteria (spec fidelity, WCAG AA, token fidelity, documentation, Storybook, Code Connect). Green / Amber / Red decision documented in writing. No further component build begins until the gate is resolved.
1b
Core component build — 15 components

Each component: Figma build (all variants, states, responsive breakpoints) + 18-section markdown spec. Priority order defined by MB. VL submits via handoff process → MB reviews against all product instances → MB approves and deploys to repo. VL does not deploy.

1c
Storybook, Code Connect & documentation

All components in Storybook with a11y addon, full story coverage at all breakpoints. Figma Code Connect linked for every component. All markdown documentation reviewed and approved by MB design. VPAT readiness assessment completed.

Track 2 In design

Screening Cases — V1 lifecycle

One case per screening context. Each case is linked to one person, one department, one check type. Assessment outcomes fold into the lifecycle — no separate column.

Cancel Invite vs Close Case — key distinction Cancel Invite is available only while the case is in an invite-phase status (Invite Link Created, Invite Link Sent, Invite Link Expiring, Invite Link Expired, Invite Email Bounced) — that is, before consent has been received. Use it when the invite was sent to the wrong address, sent to the wrong person, or placed by mistake. Cancelling revokes the link immediately. The case moves to Case History as Invite Cancelled and is terminal — to screen this person, start a new case. Cancel Invite is available from the person profile > Current Case > Invite Management, and from the table row ⋮ menu.

Close Case is only available after an order has been attempted and failed (Order Failed) or after a screening has expired without rescreening (Screening Expired). In the Order Failed scenario, PMM has already auto-cancelled the order in the backend — the case stays on "Order Failed" on screen until the admin explicitly closes it. Closing moves the case from Current Case to Case History as Case Closed. Close Case is available from: the action banner on the person profile when status is Order Failed or Screening Expired; clicking the status badge in the table row; the table row ⋮ menu; and the table selection bar for bulk-closing multiple rows.

Safety Training Cases — V1 lifecycle

One case per training engagement. Same case-based mental model as Screening Cases.

No "In Progress" case status When an applicant opens the training link or begins working through the module, that event is recorded as a timestamped entry in the case timeline — visible in the person profile. It does not change the case status. An abandoned training surfaces through link expiry, not through a silent pile.
Invite Cancelled vs Training Cancelled Invite Cancelled is used when admin cancels the invite link specifically — only available while in the invite phase (before the training is completed). Use it for wrong address, wrong person, or sent by mistake. Link is revoked immediately. Case → Training History.

Training Cancelled is the explicit "close this training case" action. Available at any point before Training Certified — including after a failed attempt (applicant did not pass). The training is cancelled in the backend; the case status stays until admin explicitly closes it. Training Cancelled is available from: the action banner on the person profile; the table row ⋮ menu; and the table selection bar for bulk cancellation.

What V1 resolves Every status describes exactly one condition — admin knows what is happening and what action (if any) is needed without opening the record. Assessment outcomes fold into the lifecycle — no separate column to cross-reference. Report Complete — Awaiting Review is explicitly visible and filterable. Invite Cancelled and Case Closed are distinct — cancelling an invite is not the same as closing a failed order or an expired screening. Invite Link Expired and Screening Expired are clearly different names for different events. Abandoned trainings surface through link expiry, not through a silent pile. Every case flows from a persistent person record, so all case history aggregates per person.
