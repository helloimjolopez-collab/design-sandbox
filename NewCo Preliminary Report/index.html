Platform Experience:
What We Found, What We
Can Fix, and What It Takes

Early insights from UX friction logs across teams and a product-wide heuristics audit of Amplify. A fuller audit is still underway. This is the pattern already emerging.

The Pattern Emerging

The same things are broken, in the same ways, in every module

Drawing on friction logs across Accounting[1] and Protections[2] and a heuristics audit of the platform[3], three things are already clear, consistent within every module and between them:

1. Unhappy paths are broken and inconsistent
Errors, loading, validation, and empty states are missing in many flows and different wherever they exist.
For example: a report renders only "$0.00" on a blank white screen, so no one can tell whether there is no data or it failed to load. Pressing Escape in another module lands on a raw server error that exposes an internal file path.
2. Interactive states are fragmented
Buttons, controls, and fields often have no hover, pressed, loading, or disabled state, and look and behave differently where they do.
For example: a user clicks Save and nothing changes, so they click again and the record is created twice. On the next screen the same kind of button does show a spinner.
3. System feedback is inconsistent
There is no shared language for success, warning, or confirmation. Toasts, alerts, and dialogs are absent in most flows and differ in every module, and permanent actions often carry no warning at all.
For example: merging two records permanently is an unlabeled icon with no confirmation step, while a routine trial upsell is styled like a critical system alert.

Different teams built these products, so each one solves the same problem a different way, or not at all. That is the pattern.

Two problems sit outside anything design can fix on its own: a single CSS rule removes every keyboard focus indicator across the whole platform, and two modules run on end-of-life frameworks (AngularJS and ASP.NET WebForms). Both need engineering ownership and are called out separately in the full audit.
What We Can Do By February

What we can realistically fix of these problems, with our current resources and on this timeline

There is no design system team, no shared code library, and tribe designers have at most 20% of their sprint time for this. Within those limits, this is what we can commit to shipping by February: a cosmetic rebrand, plus the most contained of the friction points above.

  • The rebrand. Colour and typography unified across every module, via a shared token package. This includes recolouring the navigation chrome, the top nav and side nav, to the new brand. It is a visual reskin, not a return to the navigation structure work the teams just completed.
  • A few specific navigation fixes. The search bar breaking on mobile, and the clashes between the module switcher and the side navigation. We can also add a basic universal loading state for the moments users wait, switching modules or moving between tabs, so the platform shows a loading screen or skeleton shimmer instead of appearing frozen. Small, targeted, incremental, riding alongside the recolour rather than reopening the nav overhaul.
  • Buttons, consolidated with their full set of states.
  • Input fields, consolidated with their full set of states.
  • Tables, if capacity allows. This is the first thing to fall if it does not.
Even this short list gets hard without a dedicated design system tribe and a proper initiative behind it. Each fix is specified once, but with no shared code library it still has to be hand-built in every module's own codebase. Consistency starts drifting the moment it ships. Buttons and fields survive that because they are simple. Anything more complex does not.

What users will actually notice

Being straight about the impact, so expectations are set correctly:

What genuinely improves. The product will look more modern, a little more unified, and clearly rebranded. Some core components, buttons and input fields, will start to look and behave the same across modules, including small touches like a loading state or basic motion when you click, so the most frequent interactions feel more responsive and user-friendly. A few specific annoyances go away: the search bar will work on mobile, the module switcher and side nav will stop clashing, and switching modules or tabs will show a loading state instead of appearing frozen while the platform catches up. The honest limit: without a shared code library we cannot guarantee these are applied consistently everywhere. We can try, but some fragmentation will remain, and the navigation may stay about as varied as it is today. The realistic win is a more modern, more responsive, slightly more coherent product, not a fully unified one.

What will still frustrate them. The deeper moments are not in this scope and will largely feel the same. Blank screens that do not say whether there is no data or something broke. Cryptic or raw error pages. Permanent actions with no confirmation. Dead-end screens with no way back. These are where users lose the most trust, and honestly, a rebrand does not touch them. If we ship only this, the product will look meaningfully better and feel a little more responsive, while the hardest frustrations remain.

That gap between how much better it looks and how much better it works is the case for the resourcing below.

What It Takes To Do More

The pattern is a resourcing story

This is what happens when teams are stretched thin with no shared foundation. The unglamorous moments, loading, errors, validation, empty states, are the first to be cut, then get solved downstream by engineers in isolation, the same problem a dozen different ways. A rebrand can make the platform look unified. Making it behave unified needs three things we do not have yet: a design system team, a shared code library, and a standing initiative to build on both.

Giving, Accounting, People, and Protections are the moat: the products customers choose Amplify for and stay because of. Each is complex enough to need two designers, one on new capability and one dedicated to the existing product. Accounting, given its technical depth and legacy, needs a designer whose whole role is UX quality, working close to the design system team. One designer per moat module, against a feature list that never stops growing, produces exactly what this audit shows.
