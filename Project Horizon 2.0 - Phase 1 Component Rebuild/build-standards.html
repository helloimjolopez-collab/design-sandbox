Project Horizon 2.0 · Phase 1

Build Standards

The eight completeness criteria every component must meet before it is considered done, the effort scale used throughout this audit, and the accessibility baseline required for all Phase 1 work.

V–R

Completeness Criteria

A component is complete only when all eight criteria are met simultaneously. 7 out of 8 is not complete.

⚠ Note on the ❇️ Ready for Dev marker
The ❇️ emoji on Figma page names is the "Ready for Dev" marker — it means implementation can begin. It is a starting-point signal, not a quality certification. A component carrying ❇️ may still have gaps against the eight criteria below: missing states, hardcoded values, incomplete documentation, no prototype. The eight criteria define what fully authored means.
V · Variant Economy
All required states, and only those
No speculative or redundant variants
All interaction states and variant dimensions required by the spec are present, systematically named, and organised. Equally important: no speculative, redundant, or untriggered variants exist. Every variant's presence is justified by a documented interaction requirement. Variant properties are named semantically (e.g. State=Hover, not "blue version").
N · Naming & Structure
Every layer is descriptively named
No auto-generated layer names
No auto-generated layer names ("Frame 633265", "Group 1073714087"). Every layer name reflects what it is conceptually. Library icons used throughout — no raw vectors, no embedded SVGs. Library typography styles and variables referenced directly — no inline font definitions.
T · Full Tokenisation
Zero hardcoded values, anywhere
Every property references a Figma variable
Every fill, stroke, typography property, spacing value, border radius, shadow, and opacity references a Figma variable. No hex values, rgba values, pixel measurements, or font definitions are hardcoded. Variables reference the semantic layer (e.g. text/base/primary), not primitives directly. All variable references resolve — no broken links.
D · Comprehensive Documentation
Full spec, not just a notes box
Documentation frame covers all of the below
A documentation frame exists covering: component purpose + when to use / not use; all variant properties with visual examples; interaction states; responsive behaviour; animation specs; keyboard navigation and focus order; ARIA roles, labels, and state attributes; colour contrast table; implementation notes; known edge cases.
P · Interactive Prototype
A demo that shows, not describes
All primary interaction states demonstrated
A linked Figma prototype exists that demonstrates all primary interaction states (hover, focus, active, disabled, error where applicable). Accessible directly from the component page. Shows responsive behaviour where relevant. Must be usable by a developer as a behavioural reference without needing to read the docs frame.
A · Accessibility
WCAG 2.2 AA across every variant and state
Validated per state, not just the default
All colour combinations in all states pass 4.5:1 contrast (text) and 3:1 (non-text UI). All interactive elements are keyboard-reachable with a visible focus indicator. All controls have correct ARIA roles, labels, and state attributes. Touch targets meet minimum 44×44px. Motion respects prefers-reduced-motion. A contrast table for every combination must exist in the docs frame.
M · Machine & Agent Readability
Fully consumable by agents and automated tooling
Structured, not buried in prose
All interactive elements carry unambiguous, unique accessible names. Semantic HTML roles specified in docs. All states programmatically detectable (aria-expanded, aria-selected, aria-disabled…). Documentation frame includes a structured data specification section: element role, accessible name source, state attributes, keyboard contract, expected DOM structure.
R · Fully Authored
All seven criteria confirmed, post-review
Peer design review completed
The component page has been reviewed against all seven criteria above and a peer design review has been completed. This is the fully-authored standard — distinct from the ❇️ designation, which only means implementation can begin. Criterion R confirms the design work is genuinely complete.
S–XL

Effort Scale

Estimates assume a single senior designer in Figma and include authoring, tokenisation, documentation, and review cycles.

S
Small — ≤ 3 days

Adjusting or filling gaps in an existing component — adding a missing state, resolving a token, updating docs.

M
Medium — 3–7 days

Significant rework of an existing component, or authoring a simple new atom from scratch with full documentation.

L
Large — 1–2 weeks

Complex new component with multiple variants and full documentation, or a simple organism.

XL
Extra Large — 2–4+ weeks

A full organism (e.g. Data Table with all controls) or a screen template. Should be scoped as its own work item.

A11Y

Accessibility Baseline — All Phase 1 Components

Non-negotiable requirements applied to every component authored in Phase 1.

All components authored in Phase 1 must meet WCAG 2.2 AA as a baseline. Each component's documentation frame must include all four of the following:

  • Keyboard navigation behaviour — which keys do what, focus order, trap behaviour for modals
  • Focus indicator specification — visible focus style, meets 3:1 contrast against adjacent colour
  • Screen reader label / role / state requirements — ARIA roles, accessible names, state attributes per variant
  • Colour contrast ratios — documented table covering all colour combinations in all states
