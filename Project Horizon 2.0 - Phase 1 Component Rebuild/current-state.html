Token Pipeline Readiness

Can the current Figma variable file be reliably exported into a stable token pipeline?

🔴 Assessment: Not Pipeline-Ready
The current variable file cannot be reliably exported into a stable token pipeline. Attempting to build an extraction and consumption workflow now would produce output that requires significant reworking once the underlying variable issues are resolved. Establishing the pipeline must be sequenced after the token architecture clean-up (Item 0 in the Priority Build List) is complete.

What "pipeline-ready" means

For variables to be reliably consumed into code, all five of the following conditions must hold:

ConditionRequirement
Stable, consistent naming conventionToken names follow a single predictable pattern (e.g. lowercase slash-separated: color/brand/primary) applied uniformly. Inconsistent casing, mixed separators, or spaces in names produce malformed CSS output.
Single source of truth per value typeOne active colour collection, one typography collection, one spacing collection. Multiple active collections for the same type create silent inconsistencies in export.
Clean semantic layer over primitivesComponents consume semantic tokens (text/base/primary) not primitives directly (color/black-gray/white). This is what enables theming, dark mode, and brand customisation.
Explicit include/exclude decisions per collectionA clear decision must be made for each collection before the pipeline is configured.
No broken references or hardcoded fallbacksAll variable references must resolve. Hardcoded fallbacks like var(--text-base-primary, #363636) mask broken token paths.

Pipeline blockers — summary

🔴 Emoji in a variable name: ❇️ Label/Menu/Large/Medium
CSS custom property names cannot contain emoji. Any token pipeline will fail, strip the emoji silently, or produce malformed output. The ❇️ Ready for Dev marker belongs on Figma page names only — not inside variable names.
🔴 Casing split within the semantic tier
fill/auxiliary/medium-contrast (lowercase) and Fill/Static/Info/Subtle (Title Case) are in the same tier. Style Dictionary treats casing as significant — inconsistent output. One convention must be applied uniformly.
🔴 Two active colour collections: "Color" and "Color 2 wip"
Components reference variables from both collections. Migration must complete and the old collection deprecated before any pipeline configuration is meaningful.
🔴 Variable search returns empty — likely a library publishing gap
All variable search queries returned no results despite variables being confirmed present. Verify in Figma: Variables panel → each collection → "Publish to library" toggle.
🔴 Component token layer not universally applied
Side Nav correctly uses component-scoped tokens throughout. Global Navigation uses hardcoded hex values and primitive paths. Until all components reference the component token layer, pipeline output will be inconsistent.
🟡 Typography: individual properties vs composite — requires a contract decision
Each text style has five individual variable properties plus a composite Font() reference. The pipeline should expose one contract per text style. Decide which consumers (CSS vs Blazor) need which format.
🟡 Component radius tokens carrying hardcoded values instead of aliasing global scale
Component/NavItem/Large/Radius/Radius = 8 should alias Border Radius/S = 8, not carry a standalone value. Changing the global scale will not propagate to component-level radius tokens.

A1

Token Architecture

Systemic issues that must be resolved before component authoring can proceed.

🔴 Blocking — Token Issues Must Be Resolved First
Every component authored before the token architecture is cleaned up will need to be revisited after the migration completes. The token clean-up is the pre-requisite for all other work in this project.

The Pathway system uses a three-tier token architecture: brand primitives → semantic fill/text/icon/stroke tokens → component-level tokens. This structure is sound. The issues below are not style preferences — they are blockers.

⚠️ Mid-migration: "Color" and "Color 2 wip" collections coexist
Two colour variable collections are active simultaneously. Components may reference either collection — making it impossible to audit tokenisation state accurately. The migration must complete before component work begins.
⚠️ Legacy token still active: Old/→ Card
This deprecated token is still present in the published file. It is unclear which components still reference it. Needs to be traced and removed.
⚠️ Test styles in the published file: Halo 1/2/3 Test
Placeholder/test colour styles are visible to all consumers. These should never exist in a published system file. Remove immediately.
⚠️ Typography naming is appearance-based, not role-based
Bold/M describes what the text looks like, not what it is for. Role-based names such as body/strong or heading/sm are required. Must be resolved as part of the token clean-up.
⚠️ Capitalisation inconsistency across token names
Token name casing is inconsistent across collections. A naming convention must be established and applied uniformly before pipeline configuration.
🔵 Light/Dark mode token decisions unresolved
Several components — including Button — have unresolved light/dark mode token states. The component cannot be correctly tokenised until the semantic layer clarifies which colours apply in each mode. This will affect every component with a colour-sensitive state.
🔵 Desktop/Mobile multi-mode variables not confirmed
Variable modes for responsive contexts have not been confirmed. Retrofitting multi-mode support after authoring is significantly more expensive than building it in from the start. A decision on Phase 1 scope must be made before authoring begins.
