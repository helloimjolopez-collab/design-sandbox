Track 1 Overview

What ValueLabs is building and how Ministry Brands owns the output.

How this works

MB provides the component build standards and deliverable requirements → VL builds each component to standard inside the Pathway Design System in Figma and delivers the handover spec → MB reviews and ships.

What this engagement is

Ministry Brands provides the build standards, the component requirements, and the Pathway Design System as the working environment. ValueLabs designers build each component directly inside Pathway — to standard, with all required variants, states, and tokens — and deliver a completed handover spec alongside each component. MB reviews every component against the full build criteria and ships approved work.

Collaboration model

Complex and larger components — and all templated screens — require close collaboration between VL designers and the MB design system owners. For this purpose:

Weekly sync

A dedicated 1-hour weekly meeting between VL and Jo Lopez (Sr Product Designer, Design Systems Lead) for requirements clarifications, component walkthroughs, and progress check-ins. Especially important during larger organisms and screen template builds.

Teams channel

A dedicated Microsoft Teams channel for async questions, troubleshooting, and deepening understanding of specific components or standards. VL should use this channel before making assumptions on anything unclear.

When to reach outIf a component requirement is unclear, a token is missing, an edge case is undocumented, or a larger component needs scoping — raise it in the Teams channel or bring it to the weekly sync. Do not guess and build in the wrong direction.

What VL delivers per component

Deliverable 1

Figma Component

A fully built component on a dedicated page in the Pathway master Figma file. Three required Figma sections: Components, Instances and Interaction, and Documentation. All variants, states, and visual properties built to Pathway standards.

Deliverable 2

Component Spec (.md)

A completed Markdown spec covering the 8 required sections: component overview, interaction and behaviour, content and alternate states, iconography, accessibility, motion, responsiveness, and what engineering needs.

Both deliverables are required. A Figma component without a spec -or a spec without a complete Figma component -will be returned without review.

What VL is NOT responsible for

MB handles all of the following after VL handoff. VL does not write, configure, or deploy any of these:

  • Code (React components, TypeScript, CSS)
  • Storybook stories or the Storybook deployment
  • HTML demos or interactive previews
  • Figma Code Connect linking
  • Motion / animation implementation
  • Token pipeline configuration (Style Dictionary, CSS custom property export)
  • Token architecture changes or new token creation
  • Governance documentation or design system policy co-authorship

Build Standards

The complete specification for what every component must include. These standards apply without exception.

Pathway Design System -Component Build Standards · Version 1.0 · Ministry Brands DS Team · Active

This document defines the standards you must meet for every component you build. It covers what must be in your Figma component and what must be documented in your spec. Read it before starting. Both deliverables are required for every component.

1. Your Access and Constraints

You have: Edit access to the Pathway Figma master file -build components directly inside it. Read access to the Pathway Variables library in Figma -apply tokens from it; do not modify or add to it. You do not have access to the Pathway code repository.

⚠ What you may NOT do Modify the Pathway Variables library · Add new token variables to Figma · Create pages, sections, or frames outside the component page you are assigned.

If you find that a token you need does not exist in the Variables library, do not create one. Use a raw value, flag it clearly in spec Section 17 and Figma annotations, and contact the DS team so we can add the missing token while you are in the build phase.

2. Your Deliverables

Deliverable 1

The Figma Component

A fully built component on a dedicated page in the Pathway master Figma file, built to the structural and token standards in Section 4 of this document.

Deliverable 2

The Component Spec

A completed Markdown file documenting the component to the 18-section standard. All sections complete. No [fill in] placeholders. Status: PENDING HUMAN REVIEW.

Not your responsibility: code, HTML demos, Storybook stories, Code Connect linking, motion implementation, token pipeline configuration. The DS team handles all of that after your handoff.

3. Design Standards

3.1 Tokens -the absolute rule

Critical rule Every colour, typography style, border-radius, and shadow you apply to a component must come from the Pathway Variables library in Figma. Never apply a raw hex value, raw font size, raw weight, or raw radius to any layer intended to represent the production component.

If you cannot find a token that fits:

  1. Use a raw value as a temporary stand-in
  2. Annotate in Figma where you used a raw value and why
  3. Document it in spec Section 17 with a proposed token name and priority
  4. Contact the DS team -we will add the missing token while you are in the build phase

3.2 Icons -one library only

Pathway uses Material Symbols Rounded for all icons. No other icon library, icon set, or custom SVG is permitted. Icons are sourced from the Material Symbols Figma library -use instances from this library, never embedded SVGs. The icon name in the library (e.g. arrow_forward, close) is the exact name to reference in your spec's icon table.

3.3 Typography

All type styles must use a Pathway typographic style from the Figma library. Never set raw font size, raw font weight, or raw line-height on any layer.

3.4 Accessibility -non-negotiable baseline

Required for every interactive componentVisible focus ring on keyboard navigation (must be in Figma as a Focus state variant) · Minimum 48×48 px touch target on all interactive elements · Colour contrast ≥ 4.5:1 for text, ≥ 3:1 for non-text UI elements · ARIA pattern documented in spec Section 13.0 · Full keyboard interaction in spec Section 13.3 · Screen reader announcements in spec Section 13.5

4. How to Build the Figma Component

4.1 The component page

Every component lives on its own dedicated page in the Pathway master Figma file. Match the naming convention exactly, including the emoji prefix and arrow format (e.g. ❇️ ↳ Local Navigation). Do not add components to existing pages.

4.2 Three required Figma sections

Every component page must contain three Figma sections, in this order:

SectionWhat goes in it
Components The building blocks and main component — all states, sizes, styles, and any other necessary variants organised for inspection.
Instances and Interaction The different documented instances and interactions as needed — showing how the component is used and how it behaves in context.
Documentation The full component spec (see Section 6 of this document). Responsiveness, motion, accessibility, and all other spec content lives here — not in separate Figma sections.

4.3 Building the component

Apply auto-layout throughout — every frame, every container, every nested group. Use variants to cover the full range of states, sizes, and styles the component needs. Where a part of the component can swap between different elements (an icon, a thumbnail, a leading element), use instance swaps or nested component instances. Where content is changeable or slot-based — like in cards, KPI tiles, or list items — use slots so the component stays flexible without breaking.

Apply all colours, type styles, border radii, and spacing values from the Pathway Variables library. Every visual property should reference a token. If a token does not exist for what you need, use a raw value, flag it clearly in Figma with an annotation, and note it in your spec so the MB DS team can add it.

4.4 Layer naming

Every frame, group, and layer must have a proper descriptive name — no auto-generated names like Frame 47, Group 3, or Rectangle 12. Names should clearly describe what the element is and where it sits in the component. Use a consistent naming pattern throughout, for example:

  • DataTable — the root component
  • DataTable.Row, DataTable.RowStart, DataTable.RowEnd — sub-components
  • Container.LeadingIcon, Container.TrailingIcon — named containers
  • KPITile.Value, KPITile.Label, KPITile.TrendBadge — content slots

The rule is simple: anyone opening the file should be able to understand the structure immediately from the layer names alone.

5. How to Write the Spec

The spec is a Markdown .md file. Think of it as the written specification that would otherwise exist as scattered annotations across Figma — it captures interaction behaviour, content rules, flow logic, accessibility requirements, responsiveness, and motion intent in one place. It does not duplicate what is already visible in Figma (tokens, layout, variant structure, state matrix). Every section must be complete with no placeholder text before submitting.

6. Spec sections

Each spec contains these 8 sections. All must be present and complete:

  1. Component Overview — what this component is, what problem it solves, when to use it and when not to. Include the Figma link to the component page.
  2. Interaction and Behaviour — how the component works: click and tap behaviour, hover states, keyboard interactions, how it responds to different data states (loading, empty, error), any content rules or conditional logic, multi-step flows where applicable.
  3. Content and Alternate States — collapsed, compact, read-only, or any other structural mode the component can appear in. What changes, what stays the same, and any rules governing when each mode applies.
  4. Iconography — every icon used in the component, its Material Symbols Rounded name, where it appears, and what it means. Verify every name in the Material Symbols Figma library ↗.
  5. Accessibility — the ARIA pattern the component maps to (with link to WAI-ARIA APG ↗), keyboard interaction table, focus style specification, screen reader announcement intent for each key state, and colour contrast ratios for all text-on-background combinations (minimum 4.5:1 for text, 3:1 for non-text UI).
  6. Motion — the animation intent for every transition or state change in the component. Plain language is fine — describe what moves, in which direction, triggered by what. MB engineering handles implementation.
  7. Responsiveness — how the component behaves at each of the four Pathway breakpoints: Mobile (393 px), Tablet (768 px), Small Desktop (1024 px), Desktop (1440 px). Be specific about what changes — layout, visibility, behaviour, sizing.
  8. What Engineering Needs — anything beyond the Figma file and this spec that engineering will need to implement the component: example data sets, edge case content, specific icon names, or known implementation considerations.
Storybook: Add a note at the end of the spec: "Storybook page will be created by the MB DS team after handoff." VL does not create or deploy Storybook stories.

8. Handoff Checklist

Check both lists before submitting. Do not submit if anything is unchecked.

Figma checklist

  • Component page created and named correctly
  • Three sections present: Components, Instances and Interaction, Documentation
  • Auto-layout applied throughout
  • All states, sizes, and styles covered as variants
  • Instance swaps and slots used wherever content is variable
  • All visual properties bound to Pathway Variables tokens
  • Raw values (where unavoidable) annotated in Figma
  • Every layer has a descriptive name — no auto-generated names remain
  • All icons are instances from the Material Symbols Figma library
  • Focus state variant included for all interactive components
  • Instances and Interaction section documents key usage and behaviour
  • Documentation section contains the complete spec

Spec checklist

  • Figma link filled in at the top of the spec
  • All 8 sections present and complete — no placeholder text remaining
  • Section 2 covers all interaction states, content rules, and data states
  • Section 4 icon names verified in the Material Symbols Figma library
  • Section 5 ARIA pattern named and linked
  • Section 5 keyboard interaction table complete
  • Section 5 contrast ratios verified for all text-on-background combinations
  • Section 7 covers all four breakpoints
  • Storybook note included at the end

Table: Pilot Component

The first component VL builds. The gate for the entire engagement.

⚠ Engagement gate

The Data Table is the first and only component VL builds before the full component list begins. It gates everything. No other component starts until the Table pilot has been reviewed and a Green / Amber / Red decision is documented in writing by the MB design lead.

Why the Table is the pilot

Rationale It is the most complex component in scope -widest variant surface, most extensive accessibility requirements, most token touch-points · It has the highest number of real product instances in the current Horizon application (Background Checks, Screening Flows, Child Safety) · If VL can deliver the Table to standard, the engagement has demonstrated the capability to deliver the full scope · If the Table reveals gaps, they surface at the lowest possible cost -before significant investment in the remaining 15 components

Gate decision framework

🟢

Green -Proceed as planned

Table meets full standard against all criteria. Full 15-component scope begins immediately.

🟡

Amber -Proceed with adjusted model

Specific gaps documented. MB and VL agree on adjustments before the component list begins.

🔴

Red -Renegotiate or redirect

Structural capability gap. MB assesses whether to restructure, pause, or bring work in-house.

Review criteria

All six criteria must pass for a Green decision.

  • Spec fidelity
    All variants and states per MB design, correct across all product instances in the Horizon application.
  • Accessibility
    WCAG 2.2 AA: zero critical/serious violations in automated testing. Manual keyboard + screen reader tested. ARIA correct.
  • Token fidelity
    All visual properties applied via correct semantic tokens. No hardcoded values on production layers.
  • Documentation standard
    All 18 spec sections complete. No placeholders. Machine-readable and unambiguous.
  • Storybook readiness
    All variants + breakpoints + a11y addon covered in spec. MB deploys Storybook after review -not a VL deliverable.
  • Figma Code Connect readiness
    Component structure supports Code Connect linking. MB links Code Connect after review -not a VL deliverable.
